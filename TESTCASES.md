# Тест-кейсы — вариант 2.1 API

## Основа и общие условия

Контракт: `qa-trainee-assignment-autumn-2026.md` и `postman_collection.json` из этого репозитория. Стенд: `https://qa-internship.avito.com`.

Каждая строка — самостоятельный кейс. Параметры одной строки запускаются как отдельные тесты, кроме явно обозначенных subTest. Общие предусловия: доступный стенд; Python 3.10+; новый HTTP-клиент; отсутствие зависимости от предыдущего теста. Аккаунт означает зарегистрировать уникальный username и случайный password, проверить 201/id/username, авторизоваться, проверить 200/accessToken/tokenType=Bearer и использовать этот токен. Объявление означает создать запись для id этого аккаунта с уникальным name, price=9900 и statistics={likes:21,viewCount:11,contacts:43}; проверить 200 и UUID из status. После каждого теста удалить все созданные объявления. Аккаунт без объявлений действительно пуст, поскольку принадлежит только данному тесту.

Для кейсов TC01–TC21 автоматизация находится в `test_api.py`; параметризованные тесты имеют общий префикс TC. Содержательные проверки выполняются через unittest assertions.

Для ручной демонстрации используется пользователь "Austin61" (id "21612"). Автоматизированные кейсы по-прежнему создают уникальные аккаунты: проверки новой регистрации, неизвестного пользователя и пустого списка требуют собственных свежих данных.

## Нефункциональные аспекты

- TC18 проверяет передачу Unicode без потерь.
- TC01/TC03 проверяют отсутствие поля password в успешных ответах.
- TC08 проверяет JSON Content-Type; клиент поддерживает HTTPS с обычной проверкой сертификата.
- Уникальные данные, независимые фикстуры, конечный таймаут и очистка обеспечивают воспроизводимость тестов.
- Таймаут 20 секунд является ограничением тестового клиента, не SLA сервиса. Производительность без согласованного SLA не оценивается.

## Неопределённости контракта и границы покрытия

1. Не заданы максимальные длины username/password/name и диапазон price. Поэтому не объявляем конкретный максимум, нулевую/отрицательную цену или длину 255 обязательным правилом. Полное исследование этих границ требует уточнения требований.
2. Ожидание сохранения statistics следует из принимаемого create-поля; в контракте не описаны умножение/нормализация счётчиков. TC12/TC13 не выполняют GET карточки до проверки, чтобы избежать неоднозначности учёта просмотров. Для TC21 после чтения проверяется тип и неотрицательность, а не точное число просмотров.
3. Postman упоминает 100 для statistics v2; это не определяет ожидаемый финальный успешный ответ. Для успешного чтения ожидается 200. Указание 500 в списке возможных ответов не означает, что 500 допустим при корректном запросе.
4. Автоматизирована проверка отсутствующего Authorization. Проверки подмены идентичности, обхода доступа и чужих объектов не входят в этот набор. Соответствие sellerID своему аккаунту используется во всех функциональных сценариях, но отрицательный случай несовпадения не проверен.
5. Неполное покрытие: неверные типы/невалидный JSON, недопустимые UUID, токены с истёкшим сроком, ограничения длин и нагрузка. Это оставшийся объём тестирования, а не пройденные кейсы.
6. Ни порядок, ни фиксированные идентификаторы общего стенда не используются. Точное число 2 в TC10 относится только к новому собственному аккаунту.
7. Create принимает `sellerID`, а ответы чтения фактически используют `sellerId`. Схема ответа чтения в Postman не приведена. Автотест проверяет значение поля `sellerId`; различие регистра само по себе не зарегистрировано как дефект.
